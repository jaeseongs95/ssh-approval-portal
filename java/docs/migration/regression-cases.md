# 회귀 사례 정본 (regression-cases) - ssh-approval-portal 3.0.0 Java 전환

## 0. 머리말

### 0.1 목적과 사용 규칙

- 목적: 2.4.2(Node·Python)의 시험이 고정하던 행동을 3.0(Java 25·Spring Boot·JUnit)에서도 고정하기 위한 색인이다. Java 구현 담당은 이 파일 하나로 시작한다. 어떤 사례표를 이식하는지(0.2), 사례 수와 모듈별 분포(0.3, 1절), 장부 결함 48건이 어떤 사례로 고정되는지(2절), 사례가 부족한 결함과 새로 시험할 것(3절)을 이 파일에서 찾는다.
- 이 파일은 사례표를 복사하지 않는다. 두 부분 파일의 색인과 결함 연결만 둔다. 사례의 입력·기대 결과·판정 방법·원 시험은 항상 해당 부분 파일의 사례 표가 정본이다(중복 원천을 만들지 않기 위해).
- 구현 담당은 두 부분 파일의 사례 표(0.2의 표)에 있는 모든 사례를 JUnit으로 이식한다. 한 사례는 시험 하나 이상으로 옮긴다. 시험 메서드의 `@DisplayName`에 사례 ID를 적어 추적하기를 권한다.
- 이식하지 못한 사례는 이유와 함께 「미검증」으로 남긴다. 조용히 건너뛰거나 시험을 줄이지 않는다.
- 각 사례 행의 「(추정)」은 원 시험 본문으로 확정하지 못했거나 2.x 구현 세부(Node 파일·SQLite·fd 등)를 3.0 구현 방식으로 옮긴 부분이다. 이식 전에 원 시험을 다시 읽고 확정한다.
- 삭제 표의 행은 이식하지 않는다. 삭제 사유(Node 런타임 고유, cloudflared, `codex queue`·agentapi 깨우기, vendor ssh-mcp·ssh2, Python helper 구현 세부, AIK·Jev 연구 도구, 기기 등록 토큰 결정 등)는 각 부분 파일의 삭제 표에 있다.
- 장부 결함 48건은 2026-11-12에 운영 장부(프로젝트 SSH_PORTAL)에서 조회한 값이 정본이다. 결함 ID의 접두 `SSH_PORTAL-`은 이 파일에서 생략한다(예: `D-0001`은 `SSH_PORTAL-D-0001`).

## 2. 결함 연결표 (48행, 결함마다 1행)

### 2.1 읽는 법

- 결함 상태는 2026-11-12 운영 장부 조회 값이다. VERIFIED 38건, OPEN 7건, SOURCE_FIXED 3건이다.
- 「A 사례 ID」·「B 사례 ID」는 부분 파일의 결함 연결 절(A 4절, B 5절의 결함별 요약)에서 옮겼고, 해당 사례 표의 `연결 결함` 열과 대조했다. 새로 판단해 만든 연결은 없다. 사례 ID 앞의 「확정」·「후보」는 부분 파일의 구분 그대로이다. `RC-A-`·`RC-B-` 접두는 각 묶음의 첫 번호에만 적고 뒤 번호는 번호만 적는다. `~`는 B가 쓴 연속 범위이다(예: 072~077은 072, 073, 074, 075, 076, 077).
- 「†」가 붙은 A 사례 ID(RC-A-345, 780, 790)는 A 사례 표의 `연결 결함` 열에만 있고 A 4절에는 없다. 구분 근거가 없어 후보로 취급한다. B는 열·결함별 요약·묶음별 결함 표가 모두 일치했다(193쌍). A 4절에만 있고 열에는 없는 연결은 16쌍이며 4절을 따랐다.
- 「연결 확신」: 한 결함의 A·B 연결 중 하나라도 확정이 있으면 확정, 후보만 있으면 후보, 연결이 없으면 없음이다. 부분 파일의 「후보」 중에는 근거에 「약한 연관」이 명시된 것이 많다. 후보는 결함의 행동을 직접 고정한다고 볼 수 없다.
- 「3.0에서 고정할 것」
  - 「연결 사례로 고정」: 확정 사례가 이미 그 결함의 행동을 고정한다. 해당 확정 사례를 이식하면 된다.
  - 「[계획]」: 계획 정본(`inherited-marinating-island.md`)의 「미종결 결함 10건 처리」 표 「고정 시험」 원문이다. OPEN·SOURCE_FIXED 10건에 해당한다.
  - 「(신규 제안)」: 연결 사례가 후보뿐이어서 결함 제목에서 이끈 행동 사례를 대상·입력·기대 형식으로 한 줄 제안한 것이다. 이식 대상 표에는 없는 신규 사례이므로 구현 담당이 사례로 정의하고 시험으로 만든다.

## 3. 요약

### 3.1 연결 확신별 결함 수

- 확정 32건: D-0001, 0002, 0003, 0004, 0005, 0008, 0009, 0011, 0014, 0015, 0016, 0019, 0021, 0023, 0024, 0025, 0026, 0027, 0029, 0030, 0031, 0032, 0034, 0037, 0039, 0040, 0042, 0043, 0044, 0045, 0047, 0048.

- 후보만 있는 결함은 연결 사례를 이식해도 결함의 행동이 직접 고정되었다고 볼 수 없다. 새 사례를 정의해 시험해야 한다(3.3).

### 3.2 사례가 없는 결함

없음(0건). 48건 모두 A 또는 B에 연결 ID가 하나 이상 있다. 다만 연결 ID가 있어도 후보뿐이면 결함 행동의 고정 사례가 없는 것과 같다. 그 16건이 3.3의 대상이다.

### 3.5 3.0 범위 밖 결함

없음(0건). feature-map에서 3.0 대상이 「삭제」인 45행 중 결함이 연결된 26행을 대조했다. 삭제된 것은 구현 파일이며, 결함 전체가 삭제된 기능에만 속하는 경우는 찾지 못했다. 확인한 예로 `scripts/linux-desktop-session.py` 삭제는 D-0048·0021·0022의 행동이 portal-desktop으로, 대상 helper 삭제(`scripts/install-windows-helper.ps1` 등)는 D-0001·0002·0003의 행동이 portal-ssh `SftpFileTransfer`로, `src/adapters/ssh/connection-lifecycle.mjs`·`vendor.mjs` 삭제는 D-0038·0040의 행동이 portal-ssh로 이전된다고 feature-map이 적는다. 26행 전부의 행선지를 하나씩 읽지는 않았다(미검증). 다음 두 건은 범위 밖으로 판정하지 않았고 이유를 남긴다.

- D-0037: 품질 재실행(Jev 연구)은 계획이 「E61 송신 동의 뒤(roadmap-9)」로 미루고 연구 도구 4개를 삭제했다. 3.0에서 고정할 것은 서버 런타임 JevRiskEvaluator의 응답 검증 오류 보존뿐이다.
- D-0041: 결함은 Python 시험 fixture의 umask 상속이다. JUnit fixture에는 해당하지 않으나, 연결 후보 사례(RC-B-649, 650, 662, 663. RC-B-672는 결정 D3-16으로 삭제 표로 이동)의 외부 설치 경로 안전 판정은 3.0 `AgentCliInstaller`에서도 필요하므로 신규 제안으로 두었다.

### 3.6 점검한 점
