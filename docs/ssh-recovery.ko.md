# SSH 실행 장애와 복구

1.7.1은 요청 입장 대기열, SSH 연결 회복, 실패 출력 저장 공간 계산, 실행 오류 진단을 함께 개선한다. 기존 설정·인증·정책과 명령 실행 권한은 그대로 적용한다.

## 확인한 장애 경로

- SSH 연결 객체가 연결 상태를 유지한 채 새 exec/SFTP 채널을 거절하면 같은 객체를 후속 요청에 계속 재사용할 수 있었다.
- 출력은 실행 전에 최대 16MiB를 예약한다. 실행 실패로 빈 임시 파일만 남아도 예약 전체를 최대 1시간 유지해서 실패가 누적되면 공용 128MiB 한도가 고갈될 수 있었다.
- 실행 예외가 여러 경계에서 사라져 MCP에는 출력 `unavailable`만 보였다. 이 값만으로 연결 장애와 출력 저장 실패를 구분할 수 없었다.

실제 TEST 장애에서는 Windows SSH 배너와 Linux 조회가 정상인 상태에서 Windows 실행이 실패했고, 중계기 재시작 뒤 두 대상 조회가 복구됐다. 재시작 전 내부 오류가 보존되지 않아 그 장애의 정확한 원인을 소급 확정할 수는 없다. 위 코드 경로의 재현 시험과 이 관측은 구분한다.

## 동작

최종 채널 개방 실패가 발생한 연결은 후속 별도 작업에서 회복한다. 진행 중인 다른 채널을 강제로 끊거나 실패 명령을 자동 재실행하지 않는다. 명령이 원격에 전달됐는지 확실하지 않으면 결과를 알 수 없는 상태로 남긴다. 파일 정리도 원래 연결·대상의 결속을 유지한다.

실패한 출력의 파일과 기록은 보존한다. 안전하게 확인한 실제 `.part`와 `.out` 크기로 청구량을 조정하고, 관측이 불확실하면 보수적인 예약을 유지한다. 진행 중인 작업은 전체 예약을 유지하며, 배포 보존 기준이 잡힌 동안 기존 청구량 보정은 미룬다. 1시간 TTL과 1,000개 기록 상한은 유지한다.

실행 결과의 `failure`에는 고정된 `stage`, `code`, `remoteOutcome`, `automaticReplay: false`만 포함한다. SSH 연결·채널·실행 실패, 실행 전 출력 용량 부족, 실행 후 출력 저장 실패를 구분한다. 원시 오류 문자열·스택·인증정보는 제공하지 않는다. `remoteOutcome: not_started`도 새 실행을 자동 허용하는 신호가 아니다.

입장 대기열의 크기·시간 제한과 초과 응답은 [요청 대기열](request-queue.ko.md)을 참고한다. 기존 연결이 회복됐다는 사실만으로 실패했던 작업을 재제출하지 말고, 같은 요청의 상태와 저장 결과를 먼저 확인한다.
