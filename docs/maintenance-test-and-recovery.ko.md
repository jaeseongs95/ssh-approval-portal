# 유지보수 소유권 TEST 검증과 최초 전환

이 문서는 계획이다. 아래 TEST fixture와 운영 전환은 실행 결과가 기록되기 전까지 통과로 간주하지 않는다. 기존 포털 서비스와 별도의 AWS 브라우저 SSH를 유지한다. Docker와 WSL은 시작하지 않는다.

## TEST 서버의 격리 검증

최종 통합 커밋에서 생성한 시험 번들을 고정하고 SHA-256을 대조한 후, TEST의 전용 임시 디렉터리에 새 파일로 업로드한다. 배포된 코드·DB·ENV·키 및 systemd unit은 건드리지 않는다. 임시 디렉터리는 작업별로 새로 만들고 시험 계정만 접근하게 한다. 결과에는 시험 명령, 커밋, 번들 해시, 시작·종료 시각, 종료 코드만 남긴다.

1. TEST 호스트명과 포털 서비스의 상태를 확인한다. 같은 계정의 임시 경로에서 `python3 -m unittest -v test.test_environment_helper`를 실행한다. 이 시험은 합성 ENV와 임시 state만 사용하고 실제 서비스·systemctl을 호출하지 않는다. `SSH_ENV_NATIVE_FIXTURE`는 설정하지 않는다. 새 owner 검사, release 성공·응답 불명, 예약 파일 보존과 정상/실패 복구 사례를 각각 결과에서 확인한다.
2. `node --test test/maintenance-client.test.mjs`를 실행한다. 이 시험은 로컬 loopback 합성 HTTP 서버만 사용한다. Node가 지원하는 버전인지 미리 확인한다. 구버전 capability 404에서 reserve POST가 발행되지 않는지, 두 POST가 동일 owner를 사용하고 로그에 owner가 나오지 않는지를 검사한다.
3. systemd 통합은 별도 합성 fixture가 준비된 뒤 수행한다. 임시 상태 디렉터리만 주입한 `Editor`를 만들고, scheduler는 `systemd-run --on-active=1s --collect --unit=<고유 fixture ID>`로 동일 번들의 fixture worker를 예약한다. worker는 실제 `ssh-approval-bridge.service` 대신 임시 파일에 재시작 호출을 기록하고, 합성 health·release 결과를 주입한다. owner 값은 파일이나 stdin으로만 전달하며 명령행·journal에 넣지 않는다. timer/service의 단말 상태와 fixture 결과를 별도로 확인한다. 성공, health 실패 후 복구 성공, release 응답 불명 및 중복 실행을 각각 검증한다. fixture에서 실제 broker의 고정 `HELPER`·`ENV`·`ROOT` 경로는 사용하지 않는다. 이 fixture는 아직 작성·실행되지 않았다.
4. 실제 시스템 unit·포털 경로와 연결되는 운영 검증은 별개다. 위 합성 시험은 실제 ENV socket, 실제 SSH 연결, 제품 서비스의 재시작이나 보존을 증명하지 않는다. 기능 통합 후 TEST 배포 단계에서 독립 SSH로 배포 종료와 서비스 상태를 확인하고, 최종 재시작 전 기준과 재시작 후 일관된 데이터 비교를 수행한다.

## 기존 구버전의 최초 전환

구버전은 영속 예약을 읽지 못한다. 신규 클라이언트는 capability 확인 실패 시 reserve를 보내지 않으며, 실행 중인 구버전의 자동 전환은 거부한다. 따라서 최초 전환은 운영자 관리 경로가 살아 있는 상태에서 다음과 같이 별도로 실행해야 한다.

1. 대상·현재 릴리스와 복구 파일·보존 기준을 확인한다. 독립 관리 SSH에서 기존 서비스 종료를 요청하고 완전 종료를 확인한다. 실행 중인 원격 작업은 종료 여부가 불명일 수 있으므로 별도로 기록한다. 사용자 요청에 따라 다른 작업이 존재한다는 이유만으로 대기하지 않지만, 그 결과를 보존 검증이나 예약의 증거로 간주하지 않는다.
2. 고정된 검증 패키지와 설치 명령을 사용해 정지 상태에서 신규 릴리스를 설치한다. TEST에서 동일 경로·실패 복구를 먼저 시험한다. 신규 서버가 처음 시작한 시점부터 검증까지는 이전 서버가 영속 예약을 만들어 주지 않았으므로 동시 요청이 차단됐다고 주장하지 않는다. 충돌 차단이 필요한 작업에는 별도의 접근 차단 또는 최초 진입용 bootstrap이 필요하다.
3. 새 서비스의 건강 상태, 실제 capability와 보존 결과를 확인한다. 서비스 시작 실패 또는 결과 불명 시 재시작이나 설치를 반복하지 않는다. 독립 관리 SSH에서 실제 상태를 확인한 후 수동 복구한다.

## 복구 경계

- 토큰은 root 전용 `maintenance-owner.sh`가 표시하는 파일에 보관한다. 응답이 유실되거나 해제가 확인되지 않으면 이 파일을 지우지 않는다. 같은 토큰을 사용한 상태 확인 및 복구 절차를 먼저 확정한다. 토큰 내용은 채팅, 셸 인자, 로그에 넣지 않는다.
- 구버전은 영속 예약을 강제하지 못하므로 구버전 자동 rollback은 차단한다. 이전 버전이 반드시 필요하면 서비스와 외부 접근을 독립적으로 차단한 뒤 운영자가 복구한다. 구버전이 시작된 상태를 영속 예약으로 보호된 상태라고 부르지 않는다.
- 기존 Compose 갱신 경로의 후보 이미지와 이전 이미지에 대한 영속 소유권 보장은 아직 구현·시험되지 않았다. 관련 경로를 검증하기 전에는 이 변경의 Compose 지원을 완료로 발표하지 않는다.
