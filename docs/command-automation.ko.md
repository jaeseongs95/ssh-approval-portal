# 명령셋과 독립 위험 평가

관리자 설정은 별도 `/settings` 페이지에서 관리한다. 승인 화면에도 업로드·다운로드·sudo·Jev 및 다른 모델을 통한 자동승인 중요 선택이 항상 보이며, 선택을 바꾸면 같은 입력을 유지한 채 설정 화면에서 위험도 확인·OK·저장을 진행한다. 페이지 이동에 관리자 토큰을 브라우저 저장소로 복사하지 않는다.

## 파일 자동다운로드와 실제 저장

대상별 `automaticDownloads`는 기본 꺼짐이다. 설정이 없거나 꺼져 있으면 일반 다운로드도 소유자 승인을 기다린다. 켜면 SSH 계정이 읽을 수 있는 일반 파일을 자동으로 준비하며, `elevate:true` 다운로드는 `automaticSudo`도 함께 켠 경우에만 자동으로 준비한다. 두 설정은 위험도 확인과 정확한 후보에 대한 사용자 OK로 저장한다. 다운로드 파일 내용은 Jev가 검사하지 않으며 개인정보·인증 정보가 포함될 수 있다. 기존 업로드의 덮어쓰기·sudo 전송은 계속 개별 승인을 받는다.

다운로드의 `completed`는 서버 파일 준비 완료를 뜻한다. PC 저장이나 에이전트 수신의 증거가 아니다. 다운로드 요청은 저장 카드를 직접 표시하며, Access 로그인 환경에서는 사용자 브라우저로 저장 링크를 연다. 호스트 저장이 실패한 경우에는 이미 사용됐을 수 있는 링크를 갱신한 뒤 브라우저로 안내한다. 실제 저장 완료는 기기의 파일 크기·해시로 확인하며 파일 수신을 위해 SSH 명령을 재실행하지 않는다.

## 요청 현황과 실사용 관측

요청 현황은 현재 큐에 보관된 요청을 상태별로 센다. 전체 누적 건수나 SSH 접속 상태가 아니며, 모델 평가와 실제 실행을 구분한다. 승인 이력은 별도 전체 너비 영역에서 20개씩 표시한다.

자동승인 관측 화면은 저장된 최근 24시간 명령 실행 심사만 집계한다. 사전명령·모델 자동승인, 사용자 승인, 모델 보류 후 사용자 승인, 평가 호출 시도와 기록된 토큰을 표시한다. 등록 전 평가·파일 전송·별도 읽기 호출과 사용량이 없는 실패 응답은 포함 범위를 따로 표시한다. 청구금액은 수집하지 않으며 사용자 승인과 모델 정답 여부를 동일시하지 않는다.

관리자 화면의 **자동승인 설정**을 열면 현재 설정을 불러온다. 처음 설정하는 서버에는 기본 조회 명령을 초안으로 채운다. Linux 명령을 이름이나 설명으로 검색해 고를 수 있으며, 저장된 빈 목록이나 사용자 목록은 그대로 유지한다. 명령 이름을 한 줄에 하나씩 입력하고, 필요한 경우 Jev 정보 전송과 Jev 기준 자동승인을 각각 선택한 뒤 **이 설정으로 위험도 확인**을 누른다. 피드백과 변경 내용을 읽고 OK를 체크하면 **이 서버에 저장**할 수 있다. 위험도 확인 전에는 저장 확인란을 표시하지 않으며, 내용을 바꾸거나 5분이 지나면 다시 확인해야 한다.

Jev 모델은 **Jev 도움받기** 맨 위의 선택 상자에서 고른다. 기본값은 `jev-1.14.0`이며 기존에 저장한 판본은 유지한다. 선택을 바꾸면 위험도 확인과 OK 후 저장해야 실제 호출 모델과 연결된다. 응답 모델도 선택한 판본과 정확히 일치해야 한다. 대체 평가자는 서버에 연결된 평가자만 고를 수 있으며 모델 ID를 직접 입력하지 않는다. 모델 목록은 TypeSafe 계정 메타데이터를 24시간마다 갱신하고 실패 시 한 시간 동안 재조회하지 않는다. 동시 조회를 합치며 목록 갱신이 저장된 모델 선택을 바꾸지는 않는다. API가 이동 별칭만 제공하면 배포에 포함된 판본 목록과 저장된 선택을 유지한다. Luna/Sonnet 목록은 연결된 호스트가 제공한 현재 모델을 표시한다.

Jev 기준은 `90%`처럼 표시한다. 90%를 원하면 `90`을 입력한다. 새 모델 자동 실행을 선택하면 90%를 제안하며 기존 값은 유지한다. 입력 오류는 해당 입력칸 바로 아래에 나타나고 포커스를 옮긴다. 금지 명령·대체 평가자는 **고급 설정**에서 확인한다. 기준 참조 문자열은 사용자가 기준을 선택할 때 `user-choice:` 기록으로 생성하므로 직접 입력할 필요가 없다. 이 기록은 통계적 검증 증빙이 아니다. 이전 점수 방식은 명령만 바꿀 때 그대로 보존하고, 별도 전환 버튼으로 선택했을 때만 현재 방식과 새 참조를 검토 후보에 넣는다. 확인한 후보와 참조는 저장까지 동일하게 유지한다.

`BRIDGE_COMMAND_AUTOMATION=true`로 시작하면 관리자 페이지의 **명령 자동 실행 정책**에서 대상별 정책을 설정할 수 있다. 기본값은 꺼짐이며 기존 설치의 설정과 승인 흐름을 변경하지 않는다. 활성화 직후 정책은 비어 있고 모델 실행 임계값도 없다. 기존 `read-command`는 검증된 조회 전용 경로로 유지한다. `run-command`는 활성화 시 영속 요청 경로를 사용한다.

## 파일 자동업로드

서버별 **파일 자동업로드 허용**은 기본 꺼짐이다. 기존 정책에 `automaticUploads`가 없으면 꺼짐으로 취급한다. 위험도 확인과 정확한 변경 내용에 대한 OK 뒤에 저장한 정책만 적용한다. 옵션을 바꾸면 이전 확인은 무효가 된다. 폴더 제한 없이 SSH 계정이 쓸 수 있는 경로에 새 파일을 만들 수 있어 설정·인증·자동 실행 파일에도 영향을 줄 수 있다. 파일 내용은 Jev가 검사하지 않는다. 덮어쓰기와 sudo 업로드는 계속 개별 승인을 받는다. 자동 파일 입력과 카드 파일 선택에 같은 규칙을 적용하며, 정책 변경·대상 변경·동시 실행·감사 실패로 자동 실행하지 못하면 자동 재시도하지 않는다. 업로드 자동승인은 Jev의 판정 성과와 구분한다.

## 평가 설명과 관측 캐시

승인 화면은 실제 AI 분류와 기록된 첫 미통과 조건을 먼저 보여주며 숫자는 **AI 평가 상세**로 접는다. 구체적인 위험 사유가 없는 응답에서 사유를 만들지 않는다. Jev의 confidence는 분류 점수 분포에서 계산한 참고값이며 정답률이 아니다. 새로운 `reviewReason`과 `decisionRuleVersion`은 설명용이고 실행 권한에 사용하지 않는다. 과거 이력에는 저장되지 않은 미통과 조건을 추측하지 않는다. 모델·질문·기준·분류·낮은 위험 점수의 기존 실행 조건과 저장된 threshold는 바꾸지 않는다. 새 설정의 제안값 90%와 저장된 값이 다르면 현재 저장값을 표시하고 임의로 덮어쓰지 않는다.

`assess-request-risk`는 요청별 최초 관측만 캐시한다. 같은 요청에 새 상황을 보내도 자동으로 재평가하지 않으며 `provenance.cached`, `assessedAt`, `requestState`, `additionalContextApplied`, `inputStatus`, `historical`로 출처를 구분한다. 새 입력이 적용되지 않으면 `input_changed_not_reassessed`를 반환한다. 실패도 재호출하지 않는다. 실행·등록·관측 목적과 제공된 토큰 usage·지연을 보존하며 청구 금액으로 환산하거나 실제 절감 효과라고 단정하지 않는다. 저장소의 context 지원과 클라이언트 커넥터의 종단 전달 성공은 별도이며 현재 command/target 전용 커넥터는 ssh-request-v1 호환 입력으로 상세 상황 전달을 확인했다. 실제 사용 효과를 먼저 관찰한다.

## 실행 규칙

서버의 실행 권한과 금지 목록을 먼저 적용합니다. 그다음 명령줄 전체의 실행 명령 이름을 추출합니다. 모든 이름이 사전승인 목록에 있으면 인자 위험도 검사나 Jev 호출 없이 실행합니다. 이름이 하나라도 미등록이거나 구조를 확실히 분석할 수 없으면 전체 명령줄과 상세 상황을 Jev에 보냅니다. 단순 조회인지 상태 변경인지는 이 이름 권한을 다시 제한하지 않습니다.

&&, ||, ;, 파이프와 명령 치환 안의 이름도 비교합니다. 따옴표 안의 일반 텍스트를 별도 명령으로 취급하지 않습니다. 동적 명령 이름·지원하지 않는 셸 문법·코드를 받아 다른 명령을 만드는 프로그램은 이름 목록을 추측하지 않고 전체 평가 경로로 보냅니다. 명령 이름 승인에는 인자별 제한이 없으므로 등록 전 위험도 피드백과 사용자 OK가 필요합니다. 이름이 같은 별칭·프로그램의 실제 내용이나 운영체제 권한까지 보증하지는 않습니다.

sudo는 일반 명령 위험도 JSON과 이름 목록의 권한에서 분리합니다. 서버별 automaticSudo의 기본값은 false입니다. 꺼져 있으면 sudo 요청은 모델 점수와 무관하게 개별 사용자 승인이 필요합니다. 켜져 있으면 sudo 안의 실제 명령까지 이름 목록과 비교합니다. 모두 등록됐으면 bypass, 하나라도 미등록이거나 구조가 불확실하면 전체를 Jev로 보냅니다. sudo 옵션을 확실히 읽을 수 없으면 구조를 추정하지 않습니다. sudo 허용은 사용자·환경의 운영체제 권한을 추가로 만들어 주지 않습니다.

파일 자동업로드와 sudo 체크박스는 서버별 요청 현황 아래, 접힌 자동승인 설정 위에 항상 표시합니다. 대상 서버·저장된 실제 상태·미저장 변경을 구분합니다. 변경 시 기존 위험도 확인·정확한 후보에 대한 OK·저장 절차를 사용하며 체크만으로 서버 정책이 바뀌지 않습니다. 기존 정책에 automaticSudo가 없으면 꺼짐으로 표시하고, 사용자가 저장하기 전에는 필드를 추가하지 않습니다.

src/domain/command-risks.json은 명령별 기본 위험 등급·기능·이유와 알 수 없는 명령의 기본 안내를 정의합니다. sudo 정의는 제외합니다. 등록 피드백과 검색에 공통으로 사용하며 실제 사고 확률·실행 허가·인자별 위험 판정으로 사용하지 않습니다. 따라서 높은 위험으로 정의된 명령도 사용자가 등록하고 전체 명령 이름이 일치하면 bypass합니다. 금지 목록은 계속 우선합니다.

미등록 명령이 포함된 요청은 관리자가 외부 전송을 허용한 경우에만 평가합니다. 전체 명령·상황·서버가 관측한 대상 맥락·등록 목록을 전달하고, 일부 이름만 승인됐다고 전체 명령줄을 승인된 것으로 주장하지 않습니다. sudo 체크박스가 켜진 경우에만 평가 입력의 유효 승인 이름에 sudo를 포함합니다. 알려진 비밀 입력 패턴은 외부 전송하지 않으며 비밀값을 명령이나 상황에 넣지 않아야 합니다.

명령 이름은 제출한 셸 문법에서 추출합니다. 등록한 Python·find 등의 프로그램이 인자로 받는 코드나 자체 실행 파일은 재해석하지 않습니다. 이 프로그램을 등록하면 그 인자 기능도 함께 허용하는 것이므로 등록 피드백에서 임의 실행 가능성을 확인해야 합니다. sudo 체크박스는 제출한 셸 문법에서 식별한 sudo 호출을 제어하며, 이미 허용한 프로그램 내부 동작을 격리하는 보안 샌드박스가 아닙니다. 정적으로 읽을 수 있는 sh -c와 명령 치환은 내부 명령도 비교합니다.

## 점수와 대체 평가

자동 평가 질문은 `ssh-command-risk-v4`이며 기존 관측 도구의 v1, 승인 맥락을 보내지 않던 v2와 구분한다. v4는 사용자의 명시적 사전 승인을 인정한 상태에서 전체 인자와 상세 작업 상황에 따른 실제 위험도를 판단한다. 호출자가 적은 상황은 검증되지 않은 주장으로 표시하고, 권한의 근거로 사용하지 않는다. 조회 외에도 영향이 제한된 변경과 권한 상승을 평가할 수 있다. `assess-request-risk`는 기존처럼 v1 관측 전용이며 요청을 승인하거나 실행하지 않는다.

Jev는 명령을 제안·검토하는 AI의 판단을 돕는 도구다. 점수는 사용자 사전 승인과 기존 실행 권한을 확장하지 않는다. 기준은 **안전 확률**(`probabilities.low_risk`)로 통일하며, 사용자가 선택한 0.9는 90% 이상을 통과시키는 경계다. 모델과 질문 판본·응답 분포가 유효하고 판정이 `low_risk`인 경우에 이 값 하나만 비교한다. `confidence`는 참고 정보와 응답 형식 검증에만 사용하며 별도의 실행 문턱으로 사용하지 않는다. 불확실·위험·장애 응답은 계속 수동 승인으로 보낸다.

관리자는 평가자별 `model`, `questionVersion`, `basis:'safety-probability-v1'`, `minLowRisk`, `validationRef`를 설정한다. `validationRef`는 사용자가 선택한 기준 또는 평가 근거의 참조다. 기준을 선택한 기록과 모델 품질 검증 보고서는 구분하며, 시스템이 근거의 품질을 자동 인증하지 않는다. 확률은 모델의 추정치이며 실제 사고율의 통계적 보증이 아니다. 기존 v2/v3의 `minConfidence` 결합 정책은 읽을 수 있지만 새 확률 기준의 실행을 승인하지 못한다. 웹에서 바꾸려면 새 근거 참조를 입력하고 위험도 피드백과 OK 절차를 거쳐 재등록해야 하며 묵시적으로 승계하지 않는다.

Jev는 기존 로컬 시크릿 참조와 `BRIDGE_JEV_ENABLED=true`를 사용한다. Luna 또는 Sonnet은 신뢰된 호스트가 `createApplication({riskEvaluators})`에 주입한다. 각 항목은 `{model, questionVersion:'ssh-command-risk-v4', assess(input, {signal, question, questionVersion})}`를 제공하며 같은 승인 맥락을 받는다. 결과는 `{status:'assessed', model, label, confidence, probabilities:{low_risk,high_risk,uncertain}}` 형식이다. 확률 분포·모델·질문 판본을 검증한다. 이 포트는 실제 공급자 SDK·AIK backend 연결용이며 임의 endpoint나 에이전트가 주는 점수 입력 도구가 아니다. 독립 실행형 설치에 Luna/Sonnet API 연결을 내장하지 않는다.

설정된 대체 평가자 하나는 Jev 미설정·장애·평가 불가 때만 사용한다. 유효한 위험·불확실·낮은 점수를 받은 뒤 대체 모델에서 통과를 시도하지 않는다. 평가자별 기준은 공유하지 않는다. 호출당 10초, 한 요청에서 최대 두 평가자, 모든 대상 합산 프로세스 시도 상한은 `BRIDGE_JEV_MAX_CALLS`이다. 기존 명시적 관측 도구는 별도 상한을 사용한다. 재시작하면 이 호출 예산은 초기화되며 영속 비용 상한은 아니다.

## 상태·관리·재전송

관리자 화면에서 처음 설정하는 서버는 기본 조회 명령을 미리 선택한 **초안**으로 연다. 화면을 열거나 검색하는 것만으로 등록·외부 전송·명령 실행을 하지 않는다. 이미 저장된 명령과 의도적으로 비워 둔 정책은 그대로 유지한다. 내장 Linux 명령 목록을 이름·한국어 설명으로 검색해 체크하거나 해제할 수 있고, 목록 밖 명령은 직접 입력한다. 검색 필터만 바꾸면 확인한 정책은 유지되며, 선택 목록을 바꾸면 기존 위험도 확인과 OK는 무효화된다. 등록은 아래의 위험도 확인과 명시적 OK 절차를 거친다.

`run-command`는 `evaluating` 또는 실행·승인 상태의 요청 ID를 반환한다. `get-request-status`로 확인하고 `pending`일 때만 승인 카드를 표시한다. 모델 위험·불확실·실패·기준 미설정은 사용자 승인으로 보낸다. 카드와 관리자 화면에는 판단 사유·평가자·점수를 표시한다.

실제 실행 승인 시 `approvalMode`를 `automatic` 또는 `owner`로 기록한다. 카드와 관리자 이력은 `automatic`일 때 **자동승인**을 표시하고 실행 중·완료·실패 상태는 별도로 유지한다. 자동 실행 후보라는 이유만으로 승인 대기 요청을 자동승인으로 표시하지 않는다. 이 정보는 재시작 후에도 보존한다.

관리자 전용 `GET /api/command-policy`는 revision·대상 바인딩을 반환한다. 등록은 **위험도 확인 → 피드백 확인 및 OK → 정책 저장** 순서다. `POST /api/command-policy/review`에 `{expectedRevision,policy:{targets:[...]}}`를 보내면 변경 대상의 피드백과 5분 동안 유효한 일회용 `reviewToken`을 받는다. 등록 전 평가는 별도 `ssh-command-set-risk-v1` 질문을 사용하며 `proposedCommands`만 제안으로 보내고 사용자 승인이 있었다고 주장하지 않는다. 외부 전송 허용 및 Jev 설정·예산이 있으면 실제 점수를 받는다. 평가 불가 시 불확실함을 명시하며 알려진 변경·임의 실행·전송 기능도 별도로 경고한다. sudo 이름만으로 위험 판정하지 않는다.

등록할 때 `POST /api/command-policy`에 같은 정책·revision과 `reviewToken`, `acknowledged:true`를 보내야 한다. 확인 없이 직접 등록하거나 후보를 바꾸거나 만료·사용된 확인값을 재사용하면 거절한다. 사용자 OK는 높은 위험도 피드백을 확인한 경우에도 명령 이름의 명시적 등록 승인이며, 전체 명령 이름이 등록된 실행의 Jev 평가를 생략한다. 각 대상은 `targetId,targetRevision,profile,commands,deniedCommands,externalDisclosure,modelExecution,automaticUploads,automaticSudo,fallback,thresholds`를 가진다. MCP에는 정책 변경 도구가 없다. 기존 소유자 인증과 정확한 Origin을 요구하며 stale revision·다른 대상 바인딩은 거절한다. 정책 변경 후 진행 중인 이전 자동 결정은 폐기한다. 재시작하면 미등록 피드백 확인값은 사라지므로 다시 확인해야 한다.

선택 입력 `requestKey`는 16~128자의 영문·숫자·`_.:-`로 구성한다. 같은 키와 같은 대상·프로필·명령은 기존 상태를 반환하고, 내용이 다르면 충돌이다. 키를 생략한 새 호출은 새 실행 요청이다. 자동화가 꺼져 있으면 키 입력을 거절한다.

서비스 전용 전송 디렉터리에 `command-automation.sqlite`를 0600으로 보관한다. 정책과 명령·상태를 포함하므로 비밀이 있는 명령을 입력하지 않는다. 프로세스 하나가 배타적으로 열고 FULL 동기화를 사용한다. 실행 전 상태 저장이 실패하면 실행하지 않는다. 재시작 시 평가·실행 중이던 요청은 `unknown`, 승인 대기는 `expired`로 복원하며 자동 재실행하지 않는다. 요청 10,000개에 도달하면 새 요청을 거절하므로 운영자가 보존·백업·정리 정책을 따로 수립해야 한다. 이 구현은 원격 SSH 효과의 exactly-once 보증이 아니다.

## AIK 연결

`createAikSshTool({authority,mcp})`는 신뢰된 AIK backend용 어댑터다. `authority`는 기존 AIK gateway와 영속 원장에 연결한 `authorize`, `revalidate`, `recordDispatch`, `bindRequest`, `lookupRequest`, `recordReceipt`를 제공한다. `mcp.call(name,args)`는 자격이 고정된 기존 SSH MCP 연결을 사용한다.

AIK가 만든 호출의 대상·인자·effect를 먼저 인가하고 발행 직전에 다시 확인한다. dispatch intent와 요청 바인딩은 AIK 소유 영속 기록에 저장해야 한다. `ToolSession`은 authority 구현 내부에 남고 MCP로 직렬화하지 않는다. SSH 모델 점수는 AIK 인가를 확장하지 않는다. 상태 조회는 원래 바인딩으로 수행하고 영수증은 실제 실행 상태만 보고하며 작업 완료 판정으로 해석하지 않는다. 연결 불명 시 unknown을 기록하고 자동 재전송하지 않는다.

현재 AIK 설치물의 runtime·lease·effect 계약 전체 적합성을 인증한 것은 아니다. 실제 AIK 어댑터 포트 구현과 설치물 연동 시험은 통합 시 수행한다. 이번 로컬 검증은 합성 평가자와 가짜 SSH 실행기로 이루어지며 실제 API 과금·서버 변경·모델 품질 평가·운영 활성화는 포함하지 않는다.

자동화를 끄려면 `BRIDGE_COMMAND_AUTOMATION=false`로 되돌려 재시작한다. 데이터베이스를 삭제하거나 이전 키를 재사용해 불명 요청을 재실행하지 않는다. 운영 배포 전 테스트 서버 관측·임계값 검증·독립 검토와 별도 owner 승인이 필요하다.

승인 대기는 새 요청 생성 시점부터 1시간이며 기존 요청의 만료 시각을 소급해 늘리지 않는다. `run-command`의 선택 입력 `context`(최대8192자)에 작업 목적·대상 환경·명령이 필요한 이유·영향 범위·관측 근거·복구 계획을 자세히 전달한다. AIK adapter도 같은 입력을 전달한다. Jev에는 전체 명령과 caller 상황, 서버가 확인한 대상 ID/표시명/revision/프로필/SSH 접속대상/분류/정책 맥락 및 미확인 사항을 보낸다. 상황 설명은 권한 증거가 아니고 확인되지 않은 사실은 만들지 않는다. 비밀을 포함한 상황이나 한도를 넘는 입력은 거절하며 내용을 조용히 잘라내지 않는다. 조합한 context는12288자, 전체 Jev body는 기존24KiB 한도를 적용한다. 등록 피드백과 조회 전용 평가도 가능한 상황을 함께 보낸다. 실행 질문v4는 상황 주장을 신뢰된 권한으로 오해하지 않도록 구분하며, 기존v3 임계값은 새 피드백/OK/기준 참조 없이 자동실행에 재사용하지 않는다. 조회 전용 평가에서는 저장된 상황과 추가 설명의 합계가8192자를 넘으면 거절한다.

### 상세 상황 전달과 이전 연결 호환

실행 요청에는 context로 작업 목적, 테스트/운영 구분, 대상, 예상 영향, 확인한 근거와 복구 방법을 전달합니다. 비밀값은 넣지 않습니다. 연결 도구에 context 입력이 없는 경우 command에 `ssh-request-v1:` 뒤로 `JSON.stringify({command: "실제 명령", context: "알려진 상세 상황"})`를 붙여 전달합니다. 전체 길이는 2,000자 이내입니다. 선택적으로 같은 객체에 requestKey를 넣을 수 있습니다. 서버가 명령과 설명을 분리한 뒤 기존 검증·정책·실행 경로로 전달하며, 이 문자열 자체를 셸에 실행하지 않습니다. 일반 context/requestKey 입력과 함께 보내거나 target 등 다른 키를 넣으면 거절합니다.

상황이 없는 위험 명령은 Jev를 호출하지 않고 사용자 확인으로 넘깁니다. 기존 사전승인 명령의 이름 일치 권한은 유지합니다. 과거 승인 이력에는 당시 적용한 기준과 점수를 표시하며 이후 기준 변경으로 과거 기록을 덮어쓰지 않습니다.

## 평가 설명과 관리자 표시 언어

새 요청의 `context`는 에이전트가 사실에 근거해 영어로 작성한다. 목적·환경·대상·예상 영향·확인 근거·복구 방법을 자세히 담는다. 같은 사실의 한국어 설명은 선택 입력 `displayContext`(최대 8192자)로 보내면 한국어 관리자/카드에 표시한다. 영문 UI는 원래 `context`를 표시한다. 화면 설명은 자동 번역이나 독립 확인된 사실이 아니며, 두 설명 모두 요청자의 주장이다. 실행 명령·경로·대상 식별자는 번역하거나 재작성하지 않는다.

서버는 `displayContext`를 작업 기록과 재시도 식별에 결속하지만 평가 입력 허용 목록에는 넣지 않는다. Jev로 보내는 고정 지시와 사용자 명시적 승인 사실은 영어다. 기존 요청을 소급 번역하지 않으며, 표시 언어 설정은 별도 후속 고도화다. 추가 번역 API는 호출하지 않는다. 클라이언트가 영어 평가 설명을 작성해야 하고, 서버가 임의의 문장을 자동 번역하거나 영어 여부를 보증하는 기능은 아니다.

직접 입력을 노출하지 않는 호스트는 `ssh-request-v1:` 뒤 객체에 `command, context, displayContext, requestKey`를 넣을 수 있다. 전체 2000자 제한과 외부 전송 opt-in·민감 정보 차단·기존 승인 정책은 유지된다. 별도 인자와 envelope를 섞으면 거절한다. AIK adapter도 두 설명을 그대로 전달한다.
