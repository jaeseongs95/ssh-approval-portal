# 요청 접수와 SSH 실행 대기열

1.7.2부터 HTTP 접수 대기와 SSH 실행 대기를 구분합니다. HTTP 접수는 아래의 짧은 수신 대기이고, SSH 실행 대기는 이미 자동 실행 결정이나 관리자 승인을 받은 작업의 순서를 기다리는 상태입니다.

## SSH 실행 대기

같은 대상의 실행 자리가 사용 중이거나 중계기의 실행 자리 2개가 모두 사용 중이면, 승인된 작업을 `queued`로 저장합니다. 같은 대상에서는 실행 승인이 완료되어 대기열에 들어온 순서대로 실행합니다. 서로 다른 대상은 사용 가능한 실행 자리를 함께 쓸 수 있습니다.

전체 대상의 대기 작업은 최대 32개입니다. 한도를 넘긴 새 요청은 `queue_full` / `execution_queue`로 거절하며, 이미 받은 작업을 버리지 않습니다. 대기 작업은 기존 요청의 `expiresAt`까지만 유효하고, 대기했다고 만료 시간이 연장되지 않습니다.

`queued`는 **실행 대기**이며 관리자 승인 대기가 아닙니다. 같은 요청 ID로 `wait-for-request`의 `until: completion`을 호출해 완료를 기다립니다. `until: approval`은 승인 완료로 응답합니다. 작업을 다시 제출하거나 다시 승인하지 마세요. 관리자는 실행 전 대기 작업을 취소할 수 있습니다.

이 실행 대기열은 요청 ID를 발급하는 명령·Python 소스·파일 전송·CLI 설치 작업에 적용합니다. 즉시 읽기인 `read-command`와 CLI 상태 점검은 별도이며, 대상이 바쁘면 여전히 거절될 수 있습니다. 읽기 명령도 순서대로 실행해야 하면 `run-command`로 제출하고 같은 요청 ID를 관찰하세요.

실행 직전에 대상·정책·원본 실행 계획과 만료 시간을 다시 검사합니다. 유지보수나 종료가 시작되면 아직 실행하지 않은 대기 작업은 종료하고, 실행 중 작업은 기존 종료 절차를 따릅니다. 재시작 시 저장된 대기 작업은 `unknown`으로 복구하며 자동으로 재실행하지 않습니다. 연결을 끊거나 상태 조회를 취소하는 것은 작업 취소가 아닙니다.

구버전 로컬 CLI가 `queued`를 알 수 없는 상태로 표시하면 1.7.2의 CLI/stdio 도구로 갱신하세요. MCP 연결의 도구 목록이 캐시돼 있다면 새로고침해 최신 상태 안내를 받으세요.

## HTTP 접수 대기

MCP 요청이 몰리면 인증 뒤, 도구 서버 생성과 본문 해석 전에 먼저 들어온 요청부터 처리합니다. 이 대기열은 기존 SSH 실행 제한이나 관리자 승인 이력을 대신하지 않습니다. 대기했다는 사실은 실행 승인이 아닙니다.

한 HTTP 요청에는 JSON-RPC 메시지 하나만 보냅니다. 기존 SDK가 받던 배열 형태의 배치 요청은 이제 도구 실행 전에 `400`과 `MCP_BATCH_NOT_SUPPORTED`로 거부합니다. 배치의 한 대기 호출이 처리 자리를 반환한 뒤 같은 배치의 다른 호출이 동시성 상한을 우회하는 것을 막기 위한 호환성 변경입니다. 이 거부는 명령이나 승인 요청을 등록하지 않습니다.

| 경로 | 일반 처리 중 | 접수 대기 | 최대 접수 대기 시간 | 분리된 긴 응답 |
| --- | ---: | ---: | ---: | ---: |
| MCP | 8 | 32 | 5초 | 64 |
| 관리자 | 4 | 16 | 5초 | 8 |

위 값은 보수적인 초기 상한입니다. 전체 프로세스의 메모리나 처리량을 보장하는 수치는 아닙니다. MCP 본문의 기존 1MiB 제한과 SSH 실행·파일 전송·승인 이력의 기존 제한도 계속 적용됩니다. 미완성 HTTP 본문은 30초, 헤더는 15초의 수신 시간제한을 적용합니다. 이 시간은 SSH 명령 실행 제한이 아닙니다.

일반 처리 중 자리가 남지 않으면 유한한 대기열에 넣습니다. 대기열이 차면 `REQUEST_QUEUE_FULL`, 시작 전에 5초가 지나면 `REQUEST_QUEUE_TIMEOUT`, 종료 중이면 `REQUEST_QUEUE_CLOSED`로 거부합니다. HTTP 상태는 `503`, `Retry-After`는 `1`이며 응답의 `executionAttempted:false`와 `requestSubmitted:false`는 해당 요청의 처리를 시작하지 않았다는 뜻입니다. 서버가 이 요청을 나중에 자동 실행하지 않습니다.

인증과 도구 입력 검증을 통과한 `wait-for-request`는 별도의 유한한 긴 응답 자리를 사용합니다. 긴 대기 호출이 일반 도구 호출을 전부 막지 않습니다. 이 자리가 차면 MCP 오류 `REQUEST_WAIT_LIMIT`로 응답하며 승인 대기 구독도 만들지 않습니다. 관리자 동기 승인 응답도 별도 자리를 사용하므로 승인 결과를 기다리는 동안 상태 조회·거부·유지보수 요청이 일반 자리를 쓸 수 있습니다. 관리자와 MCP의 자리는 서로 독립적이고 `/health`는 대기열 밖에서 응답합니다.

시작 전 연결 종료·대기 시간초과·서비스 종료는 대기 항목을 제거합니다. 이미 시작한 SSH 작업은 연결이 끊겼다는 이유만으로 취소됐다고 간주하거나 다시 실행하지 않습니다. 승인 요청이 이미 등록됐다면 기존 요청 번호로 상태를 확인해야 합니다. 대기열은 메모리에만 있으며 재시작 후 실행을 재생하지 않습니다.

`/health`의 `requestAdmission.mcp`와 `requestAdmission.admin`은 각각 `active`, `queued`, `detached`, `closed`와 설정된 상한을 보여줍니다. 명령·본문·인증정보는 포함하지 않습니다. 실제 서버 장애 원인과 부하 한계는 별도 관측으로 판단해야 합니다.
