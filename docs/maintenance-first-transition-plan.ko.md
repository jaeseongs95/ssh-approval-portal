# 구버전 최초 전환과 재시작 보존 검증 계획

상태: **설계안, 미구현·미실행**. TEST `ip-172-26-6-103`에서 실제 적용하기 전에 고정 후보·독립 감사·격리 시험이 필요하다. 서버를 변경하거나 Docker/WSL을 시작하지 않았다.

## 확인한 제약

기존 서비스의 온라인 maintenance는 프로세스 안의 boolean이며 owner를 증명하지 못한다. 실행·승인 대기 작업이 있으면 reserve가 거부되고, 다른 관리자가 release할 수도 있다. 사용자가 다른 작업을 기다리지 말라고 지시했으므로 대기 대신 서비스 종료를 선택할 수 있으나, 실행 중 원격 작업은 결과 불명으로 별도 기록해야 한다. 기존 boolean만으로 소유권이나 종료 후 fencing을 주장할 수 없다.

새 서비스의 preservation compare는 새 `maintenance.sqlite`에 같은 owner로 저장된 baseline을 사용하며, baseline 작성 인스턴스와 비교 인스턴스가 달라야 한다. 기존 배포에서 남긴 `offline-before.json`을 현재 API에 직접 제출할 수는 없다. 서비스 시작 이후에 처음 capture하면 그 전환의 시작 직전 데이터와는 비교할 수 없다.

현재 `createCommandState`와 `createAgentCliState` 생성자는 미완료 요청을 `unknown` 또는 `expired`로 갱신한다. `CommandOutputs` 생성자는 만료된 출력을 수거한다. 이 생성자들을 중지된 실제 DB의 읽기 전용 baseline 수집기로 호출하거나 생성 후 결과를 원본과 동일하다고 가정하면 안 된다. 이 상태 변화는 의미를 분리해 표시해야 한다.

## 최초 전환을 위한 구현 조건

1. 고정된 신규 후보를 격리 상태에서 시험한다. 이전 서버 DB의 원래 schema·요청·CLI 기록·출력 DB 및 payload를 순수 읽기 전용으로 수집해 새 비교 함수의 baseline 형식으로 변환하는 전용 도구를 만든다. 원본 DB에서 쓰기, 자동 schema 생성·마이그레이션, 출력 수거를 하지 않는다. SQLite의 종료 상태와 저널 및 파일 무결성·소유권을 확인한다. 출력 본문·저엔트로피 해시와 키는 응답·로그에 내보내지 않는다.
2. 기존 서비스가 완전히 정지된 동안 root 전용 위치에 원본 파일의 백업과 진단 기록을 만들고 비교 baseline을 고정한다. 각 DB와 파일 간 원자적 snapshot을 임의로 전제하지 않는다. 종료 전 reserve를 얻었다면 성공 응답과 해당 프로세스 세대를 기록하되, 소유권 증거로 해석하지 않는다. reserve가 거절돼도 사용자 지시에 따라 종료할 수 있지만, 진행 중 원격 작업과 재시작에 따른 정상 상태 전이는 미검증 또는 별도 진단 결과로 남긴다.
3. 새 서비스의 실제 실행 계정이 소유하는 `maintenance.sqlite`를 시작 전에 안전하게 초기화하고, 임의의 64자리 owner를 root 전용 파일에 보관한다. owner는 stdin 또는 보호된 파일로만 전달한다. 새 저장소에 owner와 정확한 baseline·기준 인스턴스 식별자를 저장하고 fsync·권한·재조회·기존 파일 충돌을 검사한다. 이미 존재하는 예약을 덮어쓰지 않는다. 이 단계는 서버 운영 데이터에 쓰는 bootstrap이므로 정확한 산출물과 실패 복구를 사전 감사해야 한다.
4. 새 서비스의 시작 코드가 maintenance 상태를 복구하기 전에 DB 초기화·출력 수거·기존 결과 migration을 수행하는 현행 순서도 검증한다. 보호 대상 또는 원본 증거가 바뀔 수 있으므로, 필요한 경우 예약 복원과 mutation 순서를 고쳐야 한다. 프로세스 기동 후 `maintenance=true`, 같은 owner, 올바른 release·health를 확인하고 기동 전 baseline과 새 인스턴스의 compare를 호출한다. 이 비교가 PASS일 때에만 최초 전환의 마지막 재시작을 검증했다고 말한다. 만료·미가용 출력은 PARTIAL로 남긴다.
5. 동일 owner의 비교 PASS, 보존 대상 범위, 설정·키·전송 staging의 별도 검사와 실제 서비스 상태를 모두 확인한 뒤 release한다. baseline 비교에는 ENV·키 원문이나 전송 staging이 포함된다는 근거가 없으므로 별도로 확인한다. 실패·부분 결과·응답 유실이면 예약과 복구 파일을 보존하고 독립 SSH로 상태를 판독한다. 인증 정보와 토큰의 내용은 로그에 남기지 않는다.

## TEST 검증과 rollback

- 합성 Linux fixture에서 실제 구버전 형식의 DB·출력 사본으로 읽기 전용 변환을 검증하고, 미완료 요청·만료 출력·손상·잠금·응답 유실·기존 예약·서비스 충돌을 시험한다. 새 서비스 시작 직후 제출을 차단하고 정상 compare 후에만 해제되는지 확인한다.
- TEST에 검증된 고정 bundle을 배포할 때 독립 AWS 브라우저 SSH를 유지한다. 스냅샷·사용자 자료의 보존, 이전 설치와 신규 설치의 manifest 결속, systemd job의 실제 종료, health와 compare 결과를 각각 확인한다. 테스트 기록과 프로세스 ID로 증명하지 않은 성공을 주장하지 않는다.
- 신규 서버를 이전 구버전으로 복구하면 구버전은 영속 예약을 무시하므로 보호가 끊긴다. 외부 접근을 독립적으로 차단하고 서비스를 정지한 상태에서만 수동 rollback을 검토한다. 구버전 실행 후 영속 fencing이 유지된다고 주장하지 않는다. 현행 자동 rollback 거부는 이 한계를 안전하게 드러낸다.

이 계획에는 아직 구현되지 않은 읽기 전용 baseline 변환기와 안전한 bootstrap이 포함된다. 그것들이 없으면 TEST·운영 최초 전환 후 전체 데이터 보존이나 완전한 소유권 보호를 완료로 판정할 수 없다.
