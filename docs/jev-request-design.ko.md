# Jev 수동 승인 감소 검증과 요청 개선

Jev 도입 목적은 사람이 승인 버튼을 눌러야 하는 상황을 줄이는 것입니다. 사용자는 원래 약80% 판정 기준을 원했지만 자동승인율이 너무 낮아51%까지 낮췄습니다. 이후 사용자는 자신의 기준을70%로 선택했고 기준은 사용자·서버마다 다르다고 명확히 했습니다. 개선 목표는 필요한 근거를 제대로 전달해 각 설정값에서 수동 승인 부담을 줄이는 것이며,70%나80%를 제품 고정 목표로 두지 않습니다. 자동승인율80% 목표와 구분합니다. 먼저 현재 요청에서 Jev가 얼마나 자동으로 처리했고 무엇 때문에 사용자 확인으로 넘어갔는지 측정합니다. 효과가 부족한 원인을 확인한 뒤 요청 방식을 개선합니다. 요청을 구조화했다는 사실이나 회귀 테스트 통과만으로 이 목적을 달성했다고 판단하지 않습니다.

현재 상태는 **세 서버 실측·두 번째 HIGH 재토론 완료, 합성 shadow 비교 도구 구현·로컬 검사 완료, 실제8+48셀 진단·사후집계 검증 완료, 실제 업무의 효과 검증 대기**입니다. 두 번째 토론은 질문·모델 의미, 순 사람 부담, 신뢰 경계, 인과 분리의 네 blind 관점과 fresh Judge로 진행했습니다. 약80% 목표가 명확해진 뒤 Judge가 해당 평가 조건을 제한 재점검했으므로 절차 보증은 partially_independent입니다. 종합 판정은 conditional_consensus이며, 실제 개선량과 충분한 효과는 아직 검증하지 않았습니다.

자동 시작 기록은 수동 승인 부담 감소의 대리지표입니다. 사용자 사후 승인은 명령 안전성의 정답이 아니며, 이 기록만으로 무Jev 대비 시간 절감이나 위험한 오승인율을 확정할 수 없습니다. 충분하다고 볼 최소 절감 목표도 아직 고정하지 않았습니다. 실제 수치부터 제시하고 판단 근거를 분리합니다.

## 원인에 따라 개선할 부분

- 문맥 누락이 많으면 에이전트가 이미 아는 목적·예상 효과·대상 범위·확인 근거·미확인 사항을 최초 요청에 포함합니다. 별도 수동 입력을 늘리지 않습니다.
- 평가 불가가 많으면 인증·연결·시간초과·예산·응답 검증부터 구분합니다. 요청 문구 변경으로 해결됐다고 세지 않습니다.
- 충분히 확인된 낮은 위험 작업이 계속 보류되면 기존 요청과 개선 요청을 같은 사례로 비교합니다. 안전하다는 주장이나 설명 분량을 늘려 통과를 유도하지 않습니다.
- 스크립트 동작·파일 민감도 등이 실제로 미확인이라면 그대로 표시합니다. hash 일치나 복구 가능하다는 설명은 동작 검토를 대신하지 않습니다.
- 모델 통과 후 시작 실패가 많으면 실행 진입·동시성 문제부터 해결합니다.

HIGH 토론은 먼저 `uncertain` 8건을 사례별로 확인하도록 결정했습니다. 실제 상세 보류 사유는 응답에 없으므로 정보 부족이 원인이라는 가설부터 검증합니다. 집계용 조회 3건도 이 8건에 포함되며 안전한 반복 업무의 대표성을 별도로 확보해야 합니다.

현행 v4를 기준선 Q0로 두고, 경계를 명확히 한 단일 Choice Q1과 필요한 효과별 Choice·코드 결합 Q2를 경쟁 후보로 비교합니다. 단일 Choice나 v4 유지가 필수는 아닙니다. 영어 입력에는 caller 주장, 실제 검증 사실, 소스·digest·완전성, 중요한 미지수를 구분합니다. 해시와 안전 주장만 있는 입력과 정확한 소스를 제공한 입력도 분리합니다. 소스 전송 동의가 기존 boolean만으로 확보됐다고 추정하지 않습니다. 현재 단계는 합성 자료만 사용하며 실제 서버 소스를 새로 읽거나 전송하지 않습니다.

## 비교·도입 조건

현행 v4의 동일 사례 결과를0.51과0.80 운영점에서 함께 비교합니다. 새 질문의0.80은 기존 v4의0.80과 동일 의미·오류율을 상속하지 않습니다. 새 질문은 shadow 답과 원점수만 기록하고 실행 문턱은 아직 부여하지 않습니다. 관측용 v1 smoke의0.999+confidence 결과를 v4 성과로 바꾸지 않습니다. 질문(Q), 같은 정보의 문자열/객체 표현(S), 소스 등 사실 보강(F)을 분리합니다. 최초 collector 한 family의8셀은 입력 민감도 진단이며 일반 품질·사람 부담 절감을 입증하지 않습니다.

대표 업무의 승인 횟수와 사람 소요시간 기준선·절감 목표를 실험 전에 고정합니다. 안전 사례에서 추가 입력을 포함한 수동 부담이 줄어야 하며, 위험·근거 불명 사례에 새로운 자동 통과가 없어야 합니다. 표본의 안전성 불확실성과 지연·실패도 사전에 정한 허용범위로 확인합니다. 관측 0건의 오류를 위험 0의 보증으로 설명하지 않습니다.

새 질문의 의미가 바뀌면 질문 판본과 검증 근거를 별도로 관리하며 기존 정책을 자동으로 재결속하지 않습니다. 품질·절감·지연을 확인한 뒤 제한된 적용에서 실제 사용자 확인 횟수와 추가 질문 부담을 확인합니다. 현재 임계값, 전송 동의, 등록 명령 bypass, sudo, 키와 실행 권한은 이 설계 작업으로 바꾸지 않습니다.

앞 절의 “아직 연결하지 않았다”는 수신부·어댑터 단계의 기록입니다. 후속 후보에서는 `run-python-source` 도구를 앱·승인 큐·관리자 원문 검토·SSH 실행 포트에 연결했습니다. 기존 명령줄을 자동 변환하지 않으며, 호출자가 이미 가진 UTF-8 코드·인자·절대 cwd와 명시적인 elevate 선택을 제출합니다. elevate=true일 때 고정 receiver 앞에 `sudo -n --`를 붙이고 이 선택도 계획 digest에 결속합니다. 모델은 같은 원문과 manifest를 문맥 안에서 받으며, 실행은 그 계획의 같은 bytes만 보냅니다. 원격 파일·의존성·사용자 권한의 실측 증명이나 샌드박스는 아닙니다.

정책에는 대상별 `sourceExecutionContract: 'python-source-v1'`를 검토·저장으로 선택하는 항목을 추가했습니다. 기본값은 꺼짐이며, 정보 전송·모델 실행·평가자별 기존 기준도 각각 필요합니다. source 요청에는 명령 이름 사전허용 우회가 적용되지 않습니다. 유효하지만 불리한 점수에 다른 모델로 재질문하지 않습니다. 임의 Python 내부의 sudo·금지 명령을 shell 이름 분석만으로 제한할 수 없으므로, sudo 자동승인이 꺼져 있거나 금지 목록이 남아 있는 정책에서는 source 자동승인을 보류합니다. 본문·인자에서 실제 차단 이름이 발견되면 거절합니다. 다른 정책을 느슨하게 바꾸거나 70%를 강제하지 않습니다.

원문은 전체 중계기 기준 최대 1MiB·100요청의 메모리에만 보관합니다. 일반 요청·감사·SQLite·MCP 결과에는 원문 대신 계획 정보만 남습니다. pending 요청의 원문은 인증된 관리자 `GET /api/:id/source`로만 읽으며 응답은 no-store입니다. 화면에서는 textContent와 높이 제한 스크롤을 사용합니다. 처리·거절·만료·입장 실패·종료 시 원문을 폐기하고, 프로세스 재시작 뒤 원문을 복원하거나 재실행하지 않습니다. requestKey와 출력의 operationDigest는 source 계획을 결속하며, 실행 예외는 결과 불명으로 남기고 자동 재시도하지 않습니다.

코드/인자/경로의 기존 민감 입력 차단은 유지합니다. 모델 입력 한도에 맞추려고 원문을 자르지 않으며, 한도를 넘으면 사용자 검토 사유를 표시합니다. 기존 관측 도구로 receiver만 평가해 source 결과처럼 보이는 경로도 거부합니다. 공개/비밀 메타데이터 경로의 과잉 차단 개선은 이번 후보에서 시행하지 않았습니다.
